### Корневая причина

Первичная: Кратковременная (43 секунды) потеря сетевого соединения между дата-центрами 
на востоке и западе США, вызванная плановой заменой оптического оборудования.

#### Вторичная (каскадная):

    Инструмент управления MySQL-кластерами Orchestrator, работающий на основе Raft, 
    корректно выполнил автоматическое переключение (failover) первичной БД на западный 
    дата-центр, так как его настройки это позволяли.

    Однако прикладной уровень GitHub был не готов к работе с первичной БД на другом 
    побережье из-за высокой задержки (cross-country latency). Это привело к массовым 
    ошибкам и деградации.

    После восстановления связи возникла критическая проблема рассинхронизации данных 
    (split-brain): восточный кластер содержал записи (несколько секунд), 
    которых не было на западе, а западный кластер уже принял ~40 минут новых записей 
    от приложений.

#### Ключевые решения и компромиссы

    Приоритет целостности данных над доступностью: Команда GitHub сознательно выбрала 
    длительную деградацию (24 часа), чтобы сохранить все данные пользователей без потерь, 
    отказавшись от более быстрых, но рискованных методов восстановления.

    Частичное отключение функций: Для предотвращения потери данных были намеренно 
    остановлены доставка webhook и сборка Pages. Это защитило метаданные, но ухудшило 
    пользовательский опыт.

#### Последствия для пользователей

    Отображение устаревшей и противоречивой информации (из-за отставания реплик) 
    в течение многих часов.

    Недоступность веб-хуков — интеграции и CI/CD системы не получали уведомления 
    о событиях.

    Остановка сборок GitHub Pages — сайты не обновлялись.

    Общая медленная работа сайта для операций записи.

    Сбойные оценки времени восстановления в статусных страницах.

### Извлеченные уроки и действия
#### Технические изменения

    Настройка Orchestrator: Запретить автоматическое продвижение первичных БД между 
    регионами, чтобы избежать неподдерживаемых топологий.

    Улучшение статусной страницы: Переход к системе, отображающей статус отдельных 
    компонентов (а не общий "красный/желтый/зеленый").

    Архитектура Active/Active/Active: Ускорение инициативы по поддержке трафика из 
    нескольких дата-центров одновременно, чтобы отказ одного из них не влиял на 
    пользователей.

    Тестирование допущений: Активная проверка гипотез о поведении системы, особенно 
    в сценариях сетевых разделений.

#### Организационные изменения

    Сдвиг в мышлении SRE: Переход от улучшения времени реагирования к проактивному 
    инжектированию отказов (Chaos Engineering) для регулярной проверки устойчивости 
    системы.

    Улучшение коммуникации: Пересмотр процесса оценки времени восстановления 
    с учетом всех переменных, включая рост нагрузки.

#### Работа с данными

    Ручное согласование: Около 954 записей в одном из загруженных кластеров требовали 
    ручного анализа и сверки для обеспечения 100% целостности данных.

### Заключение

Инцидент 21 октября был вызван каскадным отказом в распределенной системе, 
спровоцированным коротким сетевым событием. Главным приоритетом команды было 
сохранение данных пользователей, что привело к длительной деградации, 
но предотвратило их потерю. В результате GitHub пересмотрел подходы к управлению 
базами данных, архитектуре мульти-дата-центров и принципам обеспечения надежности, 
внедряя практики Chaos Engineering для предотвращения подобных ситуаций в будущем.
