### Задание

#### 1. Для платформы, которая принимает HTTP-запросы, нагружает ЦПУ вычислениями и сохраняет отчеты на диск, необходим мониторинг по методике USE (Utilization, Saturation, Errors) для ресурсов и RED (Rate, Errors, Duration) для сервиса.

Минимальный набор:

    - CPU Utilization (Загрузка ЦПУ): Процент использования (user, system, iowait). Ключевая метрика, так как вычисления грузят процессор.

    - RAM Usage (Использование памяти): Процент использования и абсолютные значения (total, used, available). Критично для предотвращения OOM-убийцы процессов.

    - Disk Space Utilization (Место на диске): Процент заполнения раздела, куда пишутся отчеты. Важно для предотвращения остановки записи.

    - Disk Inodes Utilization (Использование индексных дескрипторов): Даже при свободном месте может закончиться количество inodes при большом количестве мелких файлов.

    - HTTP Request Rate (Частота запросов): Количество запросов в секунду, показывает нагрузку на сервис.

    - HTTP Error Rate (Частота ошибок): Доля запросов с кодами 5xx от общего числа. Показывает, сколько пользователей получают отказы.

    - HTTP Request Duration (Длительность обработки): Среднее время ответа и перцентили (p95, p99). Показывает, насколько быстро платформа отвечает пользователю.

Этот набор покрывает «золотые сигналы» (Latency, Traffic, Errors, Saturation), что позволяет быстро локализовать проблему — в ресурсах или в самом приложении.


#### 2. Я предлагаю ему внедрить SLA-ориентированный дашборд:

    - Уровень доступности (Availability):

        - Что это: Процент успешных ответов сервера (коды 2xx) относительно общего числа запросов за период (например, месяц).

        - Метрика для него: «Сервис доступен 99.9% времени».

    Скорость выполнения заказа (Latency):

        - Что это: Время от отправки запроса до получения отчета.

        - Метрика для него: «95% отчетов генерируются быстрее, чем за 2 секунды».

    Надежность выдачи результата (Durability/Error Budget):

        - Что это: Какая доля запросов завершилась с ошибкой, и клиент не получил отчет.

        - Метрика для него: «Количество инцидентов с потерей отчета, бюджет на ошибки за квартал».

Эти показатели напрямую отражают выполнение обязательств перед клиентами, в отличие от системных метрик.


#### 3. Решение для сбора ошибок без бюджета

Если финансирования на полноценную ELK/EFK-стек (Grayscale / Grafana Loki) нет, нужно использовать легковесное или встроенное решение для агрегации ошибок. Лучший вариант в такой ситуации — Sentry.

Почему Sentry (или аналог вроде GlitchTip):

    - Это Open Source (можно поднять на своем минимальном сервере бесплатно или использовать бесплатный тир в облаке).

    - Он не требует построения громоздкой системы сбора логов (парсинга, индексации). Приложение просто отправляет исключения по SDK напрямую в Sentry.

    - Разработчики видят не просто поток логов, а сгруппированные ошибки с трассировкой стека, контекстом (переменные, пользователь), что гораздо полезнее, чем «сырые» логи.


#### 4. Ошибка в формуле SLA

Скорее всего, веб-сервер или балансировщик отдает коды 3xx (редиректы) или 1xx (информационные), которые не учитывает формула в числителе, но они есть в знаменателе summ_all_requests. Например, это могут быть редиректы с HTTP на HTTPS (301/302), которые составляют ~30% трафика. 

#### Исправленная формула успешности:
`(summ_2xx + summ_3xx + summ_1xx) / summ_all_requests`


#### 5. Pull и Push модели мониторинга

```markdown
Push - Агент сам отправляет метрики в хранилище: Telegraf, Graphite
  - Плюсы
    - Простота настройки за NAT/фаерволом: агент сам инициирует соединение наружу.
    - Горизонтальное масштабирование: можно слать данные в очередь (Kafka) и легко балансировать нагрузку.
    - Кастомные/короткоживущие задачи: Batch-задачи успевают отправить данные перед смертью.
    - UDP-протокол: возможность жертвовать надежностью ради производительности (StatsD).	
  - Минусы  
    - Сложнее контролировать целостность: сервер не знает, жив ли агент или просто молчит.
    - Риск DDoS: если все агенты одновременно решат отправить данные, хранилище может лечь.
    - Сложнее с конфигурацией: нужно распространять на агенты адрес сервера, токены и т.д.
```

```markdown
Pull - Сервер сам забирает метрики с эндпоинтов: Prometheus
  - Плюсы
    - Автообнаружение (Service Discovery): сервер сам находит цели (в Kubernetes, Consul и т.д.).
    - Простая проверка работоспособности: если scrape упал, сразу ясно, что цель недоступна или упала (черный ящик).
    - Единое место конфигурации: все настройки на сервере, не нужно обновлять агентов при смене retention.
    - Защита от подделки данных: сервер идет на известный IP:порт, сложнее с MITM.
  - Минусы
    - Требуется доступность endpoint'а: сервер должен достучаться до каждого агента (проблемы с NAT, сложными сетями).
    - Сложно для короткоживущих задач: прометеус может не успеть сделать scrape, 
    пока batch-задача жива (решается Pushgateway, но он нарушает чистоту модели).
    - Нагрузка на сеть от scrap'ов: при большом количестве целей может создавать паразитный трафик.
```

#### 6. Классификация систем

```markdown
    - Prometheus: Pull в основе. Короткоживущие задачи — через Pushgateway (гибридный подход, 
    но архитектурно pull).

    - TICK (Telegraf, InfluxDB, Chronograf, Kapacitor): Push. Telegraf собирает и 
    отправляет (push) метрики в InfluxDB.

    - Zabbix: Гибрид. Основа — Pull (сервер опрашивает агентов). Но есть и Push через 
    Zabbix Trapper (агенты сами отправляют данные на сервер).

    - VictoriaMetrics: Гибрид. Поддерживает оба протокола: Prometheus remote write 
    (Push от приложения/агента) и полную совместимость с Prometheus scrape (Pull).

    - Nagios: Pull в основе. Сервер Nagios сам запускает проверки через SSH, NRPE или SNMP. 
    Пассивные проверки (NSCA) добавляют элементы Push, но классический режим — Pull.
```
